# ملاحظات إصدار OUSSAMA Cutter 7.16.0-pro

## الاعتمادية عند إعادة القص

أصبحت إعادة القص عملية صريحة وآمنة من ناحية حالة المشروع. عند تغيّر قائمة المقاطع أو طلب إعادة الإنشاء، ينظف النظام المخرجات المشتقة القديمة في `final` و`final_polished` و`burned_sub` وتقاريرها، ثم يبدأ من قائمة المقاطع الحالية. لا يبقى فيديو قديم قابلاً للاختيار والرفع بعد تغيير النوافذ.

يُحفظ `cuts_manifest.json` ببصمة قائمة المقاطع بعد القص الناجح. إذا كانت البصمة مفقودة أو مختلفة، تُجبر إعادة القص بدلاً من الاعتماد على عدد الملفات وحده. كما أصبح `viral_segments.txt` يُكتب بطريقة ذرية تمنع ترك ملف JSON ناقصاً بعد انقطاع مفاجئ.

## إيقاف آمن عند الفشل

تجمع مرحلة القص نتيجة كل segment. إذا فشل ffmpeg أو بقي ملف من المخرجات مفقوداً، ترفع المرحلة خطأً واضحاً وتوقف المراحل اللاحقة؛ فلا يصل المشروع إلى Professional Polish أو رفع YouTube مع دفعة ناقصة.

كذلك أصبح `finalize_video` يعيد نجاحاً فقط بعد استخراج الصوت ونجاح mux والتحقق من ملف MP4 النهائي. وتقارن بوابة الرفع التلقائي عدد الملفات النهائية بعدد segments الحالي، فتمنع رفع دفعة ناقصة. ينطبق ذلك على InsightFace وMediaPipe وHaar، وتعود الأخطاء إلى fallback أو checkpoint بدلاً من إعلان نجاح كاذب.

## الطابور والمكتبة

يمنع RenderQueue إدخال job نفسه عدة مرات في الذاكرة عند الضغط المتكرر على resume أو start، مع بقاء recovery وإعادة retry محفوظين. وتتعرف مكتبة المشاريع على ملفات MP4 الفعلية داخل `final_polished` ولا تعتبر المجلد الفارغ مخرجاً جاهزاً.

## الموسيقى والهوية البصرية

إذا تعذر `ffprobe`، لا يفترض النظام وجود مسار صوتي بصمت. يسجل `background_music` فشل الفحص ويُبقي نسخة fallback واضحة في تقرير Polish. كما يتحقق branding من وجود ملف خرج غير فارغ بعد الشعار أو المقدمة/الخاتمة قبل اعتبار المرحلة ناجحة.

## التحقق

نجح regression الكامل بعد هذه التغييرات بعدد **717 اختباراً**، ونجح `ruff check .` و`python3 -m compileall -q .`. لا تشمل الاختبارات تسجيل الدخول إلى Google أو الرفع الحقيقي إلى YouTube، ويجب تنفيذ فحص Windows المحلي وفق قائمة القبول قبل الإنتاج.
