## 1) ما هو المشروع فعلاً (وهذه أهم نقطة)

MoneyPrinterTurbo **ليس منافساً لـ OUSSAMA** ولا امتداداً له — هو منتج مختلف في
الاتجاه المعاكس:

| | OUSSAMA Cutter | MoneyPrinterTurbo |
|---|---|---|
| المدخل | **فيديو طويل حقيقي** | **موضوع/كلمة مفتاحية** |
| المخرج | مقاطع من كلامك أنت | فيديو جديد بصوت مُصنَّع ومواد بنكية |
| العمود الفقري | القص + الأمان + منع المخالفات | التوليد الآلي بالجملة |
| الصوت | صوتك (WhisperX) | TTS (Edge/Azure/ElevenLabs…) |
| الصورة | وجهك/مشهدك | Pexels/Pixabay/AI text-to-video |
| الجمهور | صانع محتوى يحوّل محتواه | عمليات إنتاج «faceless» بالجملة |

**الخلاصة الاستراتيجية:** «الناس تقول إنه قوي» — صحيح من حيث الشعبية والاكتمال
والواجهة، لكن قوته **في نموذج منتج يتعارض مع سبب وجود مشروعك**: يوتيوب يعاقب
المحتوى غير الأصيل/المكرر/المُصنَّع بالجملة (inauthentic content)، وOUSSAMA بُني
أصلاً لتجنّب هذا العقاب. تقليد جوهر MPT = التخلي عن الميزة التنافسية الوحيدة.

لذلك السؤال الصحيح ليس «هل نقلّده؟» بل: **ما المكوّنات الهندسية عنده التي تخدم
أهدافنا دون أن تغيّر هوية المنتج؟**

## 2) ما يستحق الأخذ (مرتّباً بالقيمة، مع سبب لكل بند)

### أ. الدبلجة/التعليق الصوتي متعدد اللغات عبر TTS — **أقوى فكرة**

**الفجوة عندنا:** نترجم الترجمات (`scripts/translate_json.py`، `subtitle_language.py`)
لكن المقطع يبقى بصوتك الأصلي — فالمقطع المترجم غير قابل للنشر لجمهور آخر.

**ما فعلوه:** تجريد مزوّدي الصوت (Edge TTS مجاني بلا مفتاح، Azure V2، ElevenLabs،
SiliconFlow، Gemini TTS، Kokoro، Chatterbox…) + **توليد الترجمة من توقيتات TTS**
بدل Whisper (نمط `subtitle_provider = "edge"`) — فكرة ذكية: إن كنت أنت من صنع
الصوت، فأنت تعرف توقيتاته بالضبط، فلا حاجة لتفريغ ثانٍ.

**قيمة لنا:** تحويل قناة عربية واحدة إلى ٣ لغات دون استوديو. هذا أقرب «نمو» حقيقي
يمكن إضافته لفكرة المشروع نفسه (قصّ محتواك ونشره أوسع) — لا لفكرة أخرى.

**تحذيرات يجب حلها قبل التنفيذ:**
1. **الخصوصية:** Edge TTS **يرسل النص إلى خوادم مايكروسوفت**. المشروع يمنع خروج
   الصوت/الفيديو حالياً؛ إرسال النص قرار مختلف ويجب أن يكون **opt-in صريحاً** ومذكوراً في الواجهة.
2. **سياسة يوتيوب:** الصوت الاصطناعي يحتاج **إفصاحاً** عند التعديل الجوهري، والمحتوى
   المدبلج يمر على `originality.py` و`provenance.py` كتحويل جوهري مشروع — لا كنسخة مكررة.
3. **البوابة لا تُلمس:** أي مسار دبلجة يمر بنفس `upload_gate` و`content_guard` وDry Run
   الافتراضي وتأكيد النشر العام.

⇒ يُسجَّل كـ**المرحلة 8** في خطة الدمج بشروط قبول صارمة.

### ب. `docs/skill/SKILL.md` — توزيع موجَّه للوكلاء

عندهم «شغّل هذا الـ skill وسيتولى وكيلك التثبيت والتوليد». الفكرة رخيصة التكلفة
ومناسبة جداً لمشروع يملك أصلاً ملفات تعريفية للوكلاء: وثيقة skill لـ OUSSAMA
تعطي أي وكيل تسلسلاً آمناً (فحص قبول → قصّ مع Dry Run → تقرير) **بلا منحه مسار
نشر بلا بوابة**. أولوية متوسطة، تكلفة شبه صفرية.

### ج. أسبقية الإعدادات الموثّقة + config يُنشأ من مثال

عندهم قاعدة معلنة: **CLI الصريح > إعدادات WebUI المحفوظة > الافتراضي**. عندنا
الإعدادات موزّعة (env / CLI / WebUI / `api_config.json`) وبلا ترتيب واحد موثَّق —
وقد لمسنا هذا الضعف فعلاً في جولة التحصين (تناقض الخصوصية بين الواجهة والمنفَّذ).
درس هندسي صغير عالي القيمة: **مصدر حقيقة واحد للحسم، موثَّق ومختبَر** (ونحن بدأنا
فعلاً بـ`effective_privacy`).

### د. دفعة manifest مع فحص مسبق كامل قبل المهمة الأولى

`--batch-file`: حد 100 مهمة، فحص كل المدخلات والملفات **قبل** تشغيل أول مهمة، عزل
فشل المهمة عن التالية، وملخص JSON موحّد في النهاية. عندنا طابور دائم، لكن فكرة
«تحقق من القائمة كلها قبل أول انطلاق» تطابق فلسفة المشروع (فشل سريع وواضح).
تحسين متوسط القيمة على `render_queue`.

### هـ. قنوات توزيع لا تعتمد على GitHub Releases — **حل مرجعي لـ #27**

هذا أنفع ما عندهم هندسياً **لمشكلتنا الحالية**:
- **صورة Docker جاهزة على GHCR** (`ghcr.io/…:latest`) + `docker-compose.release.yml`.
- **حزمة Windows محمولة** (7z) + `start.bat` + `update.bat` (تحديث ذاتي بلا Releases).

نحن اليوم عالقون: المحدّث لا يقرأ إصدارات مستودع خاص (#27)، وCI لا ينشر Releases
(#25/#26). فكرة «قناة توزيع مستقلة» (صورة GHCR / حزمة محمولة) تحل المشكلة **دون**
فتح المستودع ودون الاعتماد على `checksums.txt` في Releases.

### و. البنية الطبقية `services/ controllers/ models/ config/`

تقسيمهم (`app/services` منطق، `app/controllers` مسارات، `app/models` مخططات)
أنظف من مستوى الجذر المسطّح عندنا (`scripts/` + ملفات ضخمة 2000–3600 سطر). **درس
تنظيمي لا يُنفَّذ دفعة واحدة** — يخدمه قرار «تفكيك `create_viral_segments.py`
تدريجياً» في تقييمي السابق.

## 3) ما لا نأخذه (وسبب الرفض)

| البند | سبب الرفض |
|---|---|
| **جوهر المنتج:** توليد فيديو من موضوع بمواد stock/AI | يخالف هدف المشروع: يوتيوب يعاقب المحتوى غير الأصيل المُنتج بالجملة. هذا بالضبط ما بُني OUSSAMA لتجنّبه. |
| **الموسيقى المرفقة** | المستودع نفسه يقر في الـREADME أن أغانيه «من فيديوهات يوتيوب، وإن كان هناك تعدٍّ فاحذفوها» — أي مادة غير موثّقة الحقوق. عندنا `music_fingerprint.py` وبوابة حقوق؛ استيراد هذه الممارسة تراجع. |
| **مزوّدو text-to-video** (Seedance، MiniMax H3، WaveSpeed…) | تكلفة، شروط ترخيص نماذج، ومخاطر «AI slop» — وميزتنا أن الفيديو **للمستخدم** لا مُصنَّع. |
| **واجهة API مولّدة تنشر مباشرة** | سطح API بلا بوابة/تأكيد يهدم قاعدة «لا رفع بلا بوابة». لو أُضيف API لاحقاً فيبقى Dry Run افتراضياً و`public` بتأكيد صريح. |
| **نسخ الكود (رغم أن MIT يسمح)** | المشروع نسخة GPL-3.0 معدَّلة بعمق (بوابات، checkpoint، طوابير، عربية). نقل كود أجنبي = دين صيانة + هشاشة في المسار الحرج، مقابل فائدة صفرية مقارنة بإعادة كتابة الفكرة على مقاساتنا. **نأخذ الأفكار، نكتبها بأنفسنا.** |
| **الاستدلال بـ«127k نجمة»** | لا ينقل عدوى الجودة: جمهورهم ومنتجهم مختلفان. القوة الحقيقية لمشروعنا أن يقيس نفسه بـ**recall@k** وبوابات مغلقة، لا بعدد النجوم. |

## 4) القرار التنفيذي المقترح

1. **المرحلة 8 (قيمة عالية):** دبلجة متعددة اللغات عبر تجريد مزوّدي TTS —
   Edge TTS افتراضياً (opt-in صريح مع تنبيه إرسال النص)، ترجمة موجودة أصلاً،
   وتوليد توقيت الترجمة من TTS. مقطع الدبلجة يمر بـ`originality`/`provenance`
   كتحويل جوهري **وبنفس بوابات النشر**.
2. **المرحلة 9 (تحل مشكلتنا المفتوحة):** دراسة قناة توزيع بديلة عن GitHub Releases
   (صورة GHCR + حزمة محمولة + تحديث ذاتي) كمخرج نهائي لـ#27.
3. **مكاسب صغيرة فورية بلا اعتماديات:** توثيق أسبقية الإعدادات (المصدر الواحد)،
   ووثيقة skill للوكلاء، وتحقق كامل لقائمة دفعية قبل أول مهمة.
4. **لا شيء آخر.** لا stock-footage، لا موسيقى غير موثّقة، لا text-to-video.

**شرط القبول لأي بند أعلاه:** يبقى اختيارياً أو خلف بوابة، ولا يسمح لأي backend
جديد بتجاوز `content_guard` أو `upload_gate` أو Dry Run الافتراضي أو تأكيد النشر
العام — نفس شرط خطة الدمج الحالية.
